# 18 跨服帮战修补记录

这份记录只写 18 职业这套 Frida 修补实际做过的事，以及还没做的事。16 职业只作对照，不把它的实现写成 18 已有的代码。

钩子工程在 `F:\C5\skill_c5`。跨服帮战单独一个包 `src/uniqfactionpk`，主类 `UniqFactionPkManager`。同一份 `dist/main.js` 注入 gs、glinkd、gdeliveryd。协议号跟 18 客户端。部署时把 `dist/main.js` 拷到 `/root/zxserver/hook/main.js`，先停掉旧的 `frida -p`，再挂 glinkd 和各区 gdeliveryd。中心服要先挂，再让普通服上报。

挂载脚本是 `F:\C5\skill_c5\attach_hook.sh`。它按 `/proc` 里的启动命令匹配 `./gs`、`./gdeliveryd`、`./glinkd`，逐个执行 `frida -p 进程号 -l /root/zxserver/hook/main.js`。日志在 `/root/zxserver/logs`，文件名是 `gs_hook_进程号`、`gde_hook_进程号`、`glink_hook_进程号`。已经挂过的进程会跳过。gamedbd 不挂。

## 已经做的

### 打开窗口不再掉线

申请窗是 `Win_Battle_UniqFaction_WarApply`。打开时先做客户端时间判断（`0x8098C0`），再发 6904（区服列表），接着发 55629（宣战查询）。这两个号在 18 的 glinkd、gdeliveryd 里原来都没有登记。

glinkd 的 `Protocol::CheckPolicy`（`0x805E906`）对未登记的号打 `Protocol Unknown` 后抛异常，连接被拆掉。桩登记上之后，号不在状态表里，则打 `Protocol StatePolicy error`，同样抛异常。本地 link 上看到的就是 `type=6904,size=8,state=GDataExchgServer`。

`gnet.ts` 在 glinkd 和 gdeliveryd 里为这套协议登记自定义桩。`CheckPolicy` 只改入口 6 个字节，进一小段可执行代码：跨服帮战这套协议号直接通过，其它协议继续原来的检查。整段替换曾经把 gdeliveryd 打崩，不能退回那种做法。

客户端请求由 glinkd 记下角色和会话后转给 gdeliveryd。gdeliveryd 组回包，再按角色送回对应的 link。回包发到这次请求保存的会话上。

### 区服列表和帮派列表

6904 只在打开窗口时发。切区是 `Lst_Sver2`，再点一次区服也走 6906。这个窗口没有单独的刷新按钮，55629 也不在刷新时重发。

| 方向 | 协议 | 现在的行为 |
| --- | --- | --- |
| 区服列表 | 6904 / 6905 | 回配置里出现过的每个区号。没有配置时，中心服回已经上报的区，普通服只回本区 |
| 某区帮派列表 | 6906 / 6907 | 按包里的目标区号回该区帮派。6907 字段顺序是区号、角色、目标区、帮派数组、localsid |
| 帮派一项 | — | 区号、帮派 id、等级、活跃、帮派名。名字是 UTF-16LE |

`activity` 是帮派活跃度，对应 `factionmanager.h` 里每周周榜清掉的那个值。写在配置里只改变列表上显示的数字，不写帮派库。`level` 为 0 时向 `FactionManager::GetLevel`（`0x8436F0A`）要等级。

帮派名单的配置文件是 `/root/uniqfaction.json`。每次处理 6904、6906 都重新读，所以再点一次区服就能看到刚改的文件。`faction` 为 0 的行跳过。没写 `zone` 的行算本区。文件里有帮派时，玩家所在的这台机器直接回答，不再把 6904、6906 转给中心服。两个区的进程在同一台机器上时，读的是同一个文件，一份里写上两个 `zone` 即可。

```json
{
  "factions": [
    { "zone": 1, "faction": 1001, "name": "一区帮派", "level": 0, "activity": 10000 },
    { "zone": 2, "faction": 2001, "name": "二区帮派", "level": 0, "activity": 8000 }
  ]
}
```

文件没有，或名单为空时，读 `TopManager` 的帮派活跃榜：先键 1036，没有再读键 36。表 36 是活跃周榜，`UpdateTop` 把当周数据留在键 36，要等 gdeliveryd 重启才拷到 1036。`GetTopFactionTable` 读的是表 31，不用那张表填 6907。

普通服在已经连上中心服时上报 6902，中心服用 6903 要求重报。中心服按区号分开保存。非强制上报有 2 秒间隔，收到 6903 时立刻重报。配置里有多个区时，每个区各发一条 6902。

第一次能画出帮派列表，是因为 6907 改成了客户端要的字段顺序。切区和再点区服能换名单，是因为 6906 按目标区号过滤，并且有配置时在本机回答。

### 宣战已经去掉

申请不再读宣战表，服务端也不再按帮派保存宣战。窗口打开时客户端仍会发 55629、55627，回包只是为了不拆连接：查询回空列表，查自己的回「未宣战」。写入和删除也不再记录。

### 挑战和房间

点「申请帮战」并在确认框选「是」之后发 6886。目标帮派要在当前这份帮派名单里，名单和 6907 同源。不在名单里回 5。

在名单里时，到目标帮的帮派库查在线帮主和副帮主，给他们发 6890。客户端弹出同意或拒绝。有人同意才给申请人和应战的人发 6892。同帮其它在线成员，按帮派在线名单再各发一条。都拒绝回 50，都不在线回 48，300 秒没人应回 51。目标区和本区相同直接回 70，不发邀请，客户端按原来的同区提示显示。跨区由申请人所在的交付服把 6910 送给中心服，中心服再转给目标区；目标区没挂上这份脚本，或者中心服没连上，邀请送不出去。

点申请之后客户端立刻说「玩家已下线」，是返回码 5。这句不是帮主下线。帮主和副帮主都不在线是 48，界面是「被挑战帮主不在线」。5 表示邀请还没离开申请人这一区：帮派不在这份名单里，或者中心服没连上。游戏自己的日志不写这一步，要看申请区 `gde_hook_进程号`。送出去会有「已交给中心服」，没连上会有「中心服没连上」。6910 和 6911 跟其它协议一起登记，中心服和目标区才收得进。glinkd 已经把申请转给交付服之后，不再自己回 5。

同意之后左上角按钮来自 6892。小退、大退再进游戏时，客户端上的这个状态清掉了。16 在选角进入后的 `GetUIConfig` 里把还没结束的跨服帮战再发一次 6892。现在也这样：这一区的交付服内存里还有进行中的房间，帮派成员再登录就补一次开战。交付服进程重启后这块记忆不在。已经试过：小退、大退再登录，左上角按钮还在。

计分板 6895 和房间列表里的帮派名，用申请时存下的 UTF-16LE 名字。名字空的才退回显示帮派 id。已经试过，计分板上是帮派名。

有人同意之后，开战房间先用 6912 送到中央，再去开房。中央副本 gs 的 6900 写下真实结束时间，击杀 6658 记在这场房间上，再送回攻守两个本区。6894 查分用的仍是开战房间号，试过是 1，不是世界索引 5001。

gs 的 `uniq_mafia_battle_raid_world_manager::OnCreate`（`0x8B5A3E6`）、`OnClose`（`0x8B5A3EC`）在返回后发 **6900**。交付服只在房间号已经对得上时更新这块内存房间。`gmatrix::IsInUnique` 没有改。

### 进入跨服副本

本区交付服没有登记地图 525 时，不在本区开房，向中央送开房。中央在已经登记 525 的副本 gs 上发 `SendRaidStart`，类型 18，记下世界索引，并丢掉游戏随后要关掉这个副本的包。试过：中央 gs 402，模板 1422，地图 525，房间 1，世界索引 5001。

点「进入战场」从人所在的本区 gs 发出。本区把进房转到中央，中央把 `CrossRaidEnter_Re` 送回本区。本区先让玩家所在的 gs 做进场检查。检查通过后，把回包里的副本类型从 18 改成 19，走原来的 `TryChangeDS`，目标线是中央那条副本 gs。

客户端按中央区号去 `configs\crossserverlist.txt` 找中央 glink。试过的中央区号是 2031，第三列必须是这个区号。对不上时，客户端断开后不会再连。

中央给跨服角色另编一个号。试过原角色 1029，中央号 1041。登录用中央新号。进房记录先按原号记下，存档回包里对上新号之后，登录时把副本线和世界索引写进登录包。已经试过，人可以进到副本里。

模板 1422 原来的等级上限是 170。人物超过上限时，本区检查回 51，客户端显示「等级不够，无法执行此操作」。本区 gs 和副本 gs 都要有这份模板，地图是 525，并且等级范围盖住人物。副本 gs 启动后要把 525 报到中央交付服。

当前钩子是 `dist/main.js`，107 KiB（110069 字节）。88.3 KiB 那一版会在副本 gs 回 6900 时把开战包写进 gs 连接，进房会超时断线。这一版改掉了。

计分板可以打开，击杀数能记上。已经试过。成员一行是角色号、杀敌数、被杀数、帮派 id、名字。名字取角色身上的 Octets：数据指针在人物信息 `+0x10`，字节长度在这块缓冲区前面 8 个字节。之前把指针当成了长度，界面上名字是 1 和 0。杀敌数加在击杀的人那一行，被杀数加在被杀的人那一行。名字这一处已经编进当前这个包，游戏里还没再对过界面。

### 返回下界不用改钩子

副本结束后人回到中央 gs 的跨服线。点 NPC「返回下界」是原版离场服务 `crossserver_out_executor::OnServe`（`0x886bd02`）。战斗中直接失败，不发包。仙魔等级是 `gplayer_imp+0x2f4` 的短整数，大于 0 才放行；等于 0 时再看 `CheckGMPrivilege`（`0x86e0838`）。两道都不过，服务返回 0，交付服看不到 `PlayerTryChangeDS`。过了才发 `PlayerTryChangeDS`，flag 是 2，也就是回家。

二区角色仙魔等级是 0，普通权限点了没反应。设成 GM 之后能下去。一区能下去，是那些角色仙魔等级大于 0。这次核对时没有挂钩子。本区角色若还冻着（`remote_central_type=1`），在本区选角会走 `TryRemoteLogin`，flag 3，把人再送回中央 111 线。等 flag 2 的返回完成，冻结才会清掉。

## 这一版加上的

申请时间按界面上的 12:00 到 21:45。这段以外回 93。申请人职位看人物信息 `+0x38`，必须是帮主 2 或副帮主 3，否则 41。帮派等级用 `FactionManager::GetLevel`（`0x8436F0A`），小于等于 0 回 45。守方收到邀请时也查自己的等级，并且查是否已在本服帮战。本服帮战只把 47 当成失败，冷却 46 不拦。同区仍是 70。繁荣度 49 没接。

挑战前向申请人所在的 gs 发 6913，查物品 71560，至少要有 1 个。没有就回 16。gs 四秒没回，回 5。对方同意之后再发一次 6913，扣掉 1 个。扣失败只记日志，帮战照样开。6913、6914 只在交付服和 gs 之间走，不转给客户端。gs 的 `CheckPolicy` 入口是 7 个字节，这两个号在 gs 上单独登记。

接受之后，攻守两边的在线成员都会收到 6892。名单在帮派详情 `+0xfc`，链路号在 `FamilyRole+4`，角色号在 `+0x30`。帮战进行中才上线的人，仍是选角进入后补发 6892，这一段原来就有。

战场人数在中央进场登录时按阵营累加，中央角色下线时减掉，再用 6912 送到本区。6895 里攻方人数、守方人数用这两个数。观战人数和观战资金仍是 0。

房间从进行中变成结束时，本区和中央各发一条世界频道广播。文案在 `broadcast.ts` 的 `warBroadcastText`，时期目前只有结束。以后要换不同时期的句子，在 `WarPeriod` 里加名字，并在这个函数里加一句。发送仍是世界频道。不发物品，不写帮战记录。配置和排行榜仍只决定申请窗里的名字和数字，不写帮派库。
